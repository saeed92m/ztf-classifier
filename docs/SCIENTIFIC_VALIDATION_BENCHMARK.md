# Scientific Validation & External Benchmark Contract

## Purpose

This document defines the permanent scientific-validation gate for ZTF Classifier and the broader Astronomical Data Analysis & Discovery Platform.

The goal is to verify the product against independent, externally sourced reference data and labels, rather than relying only on internal unit tests, model agreement, or training-set performance.

A release is not scientifically accepted merely because the software tests pass. The release must also demonstrate that the scientific pipeline produces correct, reproducible, and appropriately qualified results on controlled external benchmarks.

## Core principle

Ground truth, reference predictions, and internal model output are separate evidence layers.

Agreement with another classifier is not treated as ground truth by itself.

The validation system must distinguish:

1. independent labeled ground truth;
2. external catalog/cross-match evidence;
3. independent classifier/reference-system outputs;
4. raw/source-backed ZTF observations;
5. internal predictions and diagnostics.

## Required validation layers

### Layer A — Independent labeled benchmark

Use datasets with externally established labels that are not generated by the ZTF Classifier model being evaluated.

Initial benchmark candidates include:

- StarEmbed ZTF_40k: approximately 42.6k multi-band ZTF light curves, with train/validation/test splits and an additional anomaly/OOD split. It exposes seven in-distribution variable-star classes and a disjoint anomaly split. The dataset is distributed in Parquet format.
- ZTF Catalog of Periodic Variable Stars classification release: 730,184 periodic transients with class labels and SIMBAD cross-match results.
- Original ZTF Catalog of Periodic Variable Stars: 781,602 periodic variables classified into 11 main types.

These sources have different provenance and class taxonomies. They must not be silently merged into one universal label space.

### Layer B — Catalog/cross-match validation

Where scientifically appropriate, compare classifications and object identity against independent catalogs such as SIMBAD and other explicitly documented survey/catalog sources.

Cross-match evidence must preserve:

- source catalog and release/version;
- object identifier;
- coordinate matching rule;
- angular tolerance;
- match multiplicity/ambiguity;
- source label;
- retrieval timestamp;
- license/provenance metadata.

A catalog label is evidence with documented provenance, not an unconditional universal truth.

### Layer C — Independent classifier/reference system

ALeRCE may be used as an independent reference system because its public services expose ZTF objects, detections, classifications/probabilities, and machine-learning features.

ALeRCE outputs must be stored as reference predictions, not silently promoted to ground truth.

The validation framework must record:

- ALeRCE service/API/TAP source;
- classifier/version where available;
- retrieval timestamp;
- object ID;
- returned class/probability data;
- schema/version;
- query parameters or manifest reference.

Current ALeRCE data access should use the public API/TAP services rather than assuming that the older direct database connection is a future-proof interface.

### Layer D — Raw ZTF/source-backed reproduction

Use source-backed ZTF observations to verify that:

source -> ingestion -> validation/QC -> normalization -> feature generation -> inference

produces deterministic and auditable results.

ZTF public Data Release 24 is a useful pinned release reference. DR24 covers March 2018 through October 2025 and contains billions of detections/light curves. The benchmark harness must use a small, versioned subset rather than attempting to put the full release into Git.

### Layer E — OOD and failure-case validation

The validation suite must explicitly include:

- unseen classes;
- sparse light curves;
- missing bands;
- malformed observations;
- duplicated observations;
- invalid/NaN/inf photometry;
- extreme cadence;
- outlier contamination;
- insufficient detections;
- source/API failures;
- ambiguous cross-matches;
- confidence/calibration edge cases.

OOD results must remain separate from ordinary classification metrics.

## Benchmark manifest contract

Every benchmark dataset used for release validation must have a machine-readable manifest containing at minimum:

- benchmark identifier;
- dataset name;
- source URL/DOI;
- exact release/version;
- retrieval date;
- license;
- file/object identifiers;
- cryptographic hashes where practical;
- schema version;
- label taxonomy/version;
- class mapping;
- split definition;
- leakage exclusions;
- preprocessing contract;
- expected input contract;
- ground-truth provenance;
- reference-system provenance;
- benchmark generation code/version.

Large scientific data files remain external to Git. Git stores manifests, checksums, benchmark definitions, expected metadata, and reports, not bulk source data.

## Leakage prevention

The benchmark system must explicitly prevent:

- training/test object overlap;
- object-level duplicates across splits;
- target leakage through labels or derived features;
- future observations leaking into historical evaluation;
- model artifacts trained on benchmark test objects;
- benchmark-specific preprocessing being applied inconsistently;
- tuning thresholds against the final test set.

Any benchmark used for model selection must have a separate untouched final evaluation split.

## Metrics

The benchmark evaluator must report, as applicable:

### Classification

- accuracy;
- balanced accuracy;
- macro precision;
- macro recall;
- macro F1;
- weighted metrics where useful;
- per-class precision/recall/F1;
- confusion matrix.

### Probabilistic quality

- log loss where applicable;
- Brier score where applicable;
- calibration diagnostics;
- reliability information;
- confidence distributions.

### OOD

- OOD detection metrics appropriate to the benchmark;
- coverage/rejection behavior;
- false-accept and false-reject analysis;
- class-conditional failure analysis.

### System/scientific integrity

- feature-generation determinism;
- schema compatibility;
- provenance completeness;
- observation/QC acceptance rate;
- inference reproducibility;
- failure-code correctness;
- latency/resource measurements where relevant.

No single scalar metric is sufficient for scientific acceptance.

## Expected outputs

Each benchmark run must produce machine-readable and human-readable evidence:

- benchmark manifest;
- run metadata;
- per-object predictions;
- probabilities/diagnostics;
- reference labels;
- comparison results;
- confusion matrix;
- per-class metrics;
- OOD metrics;
- calibration diagnostics;
- failure cases;
- provenance;
- software/model/data versions;
- final validation report.

## Regression policy

A benchmark becomes a regression fixture once its manifest and reference evidence are frozen.

Every release candidate that changes:

- feature generation;
- preprocessing;
- model loading;
- model selection;
- inference;
- calibration;
- conformal diagnostics;
- OOD diagnostics;
- observation normalization;
- scientific API contracts

must run the relevant benchmark suite.

A regression is a release-blocking event until investigated and explicitly accepted with documented scientific justification.

## Acceptance gate

The final production acceptance checklist must include a dedicated scientific-validation gate.

The gate is passed only when:

1. benchmark manifests are pinned;
2. ground-truth provenance is documented;
3. leakage checks pass;
4. external benchmark execution succeeds;
5. metrics and diagnostics are generated;
6. reference-system comparisons are clearly separated from ground truth;
7. OOD/failure cases are evaluated;
8. results are reproducible from the recorded manifest;
9. any regression is explained and resolved or explicitly dispositioned;
10. evidence is attached to the release acceptance record.

## Initial benchmark strategy

Implementation should proceed in stages:

1. establish a small deterministic benchmark subset from StarEmbed and/or the existing controlled benchmark;
2. establish catalog-backed labeled cases from the ZTF periodic-variable datasets;
3. add independent ALeRCE reference comparisons;
4. add a pinned ZTF DR24 source-backed reproduction subset;
5. add OOD/failure-case suites;
6. automate the complete validation gate in CI or a release workflow without downloading multi-gigabyte data on every ordinary unit-test run.

The first benchmark should optimize for scientific traceability and reproducibility, not dataset size.

## Scientific interpretation rule

A benchmark result must never be presented as proof that the product is universally correct.

Reports must state:

- what population was evaluated;
- what labels mean;
- which source/release was used;
- what observations were available;
- what classes were covered;
- what was not tested;
- what limitations apply.

The product may claim only what the evidence supports.

## Evaluation-role contract

Every benchmark manifest must explicitly declare whether its labels are `ground_truth` or `reference_system` evidence.

A `reference_system` benchmark such as ALeRCE must use a reference-specific label field and provenance. Its predictions may be compared with the product output, but they must never be represented as ground truth or satisfy a ground-truth provenance requirement.
